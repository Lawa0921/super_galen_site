# 撰寫 SuperGalen 文章

產出一篇主題聚焦、具有作者觀點、證據與推論界線清楚，且符合 Galen 個人風格的文章。不要把「寫得完整」誤認為「把所有相關題材都塞進同一篇」。

## 核心原則

1. **一篇只服務一個核心問題。** 使用者提過的 AI、程式開發、遊戲、心理學、投資等題材，是可分別撰寫的範圍，不是每篇文章的必填元素。
2. **先找觀點，再找資料。** 用一句話寫出本文要增加的判讀；若只能寫出「AI 有風險」「工具仍需人工審查」等通用結論，先繼續思考，不要開始堆資料。
3. **資料支撐觀點，不代替觀點。** 摘要來源不等於文章。清楚回答「讀者看完後，多得到哪個判斷方法或具體主張？」
4. **區分事實、證據與作者推論。** 不把合理推測寫成研究結論，也不把「官方沒有公布」改寫成「已證明功能不可靠」。
5. **風格來自作者既有文章，不來自固定模板。** 不要每篇都機械套用「想像一下／我的觀點是／表格／三條規則／帶走三句話」。
6. **沒有獨立 ground truth，就不要宣稱完成校準。** 檢查評估結果是否已被待評估的提示、模型或介面影響。

## 工作流程

### 1. 確認工作環境

- 在開始前確認目前 branch、worktree 與目標檔案。
- 保留 worktree 內所有無關改動，不清理、不回復、不順手修改。
- 新文章放在 `src/content/blog/YYYY-MM-DD-slug.md`。
- 若已有專用文章 worktree 或 PR，繼續使用，不另開重複分支。
- 讀取 `AGENTS.md`、`CLAUDE.md` 與 `docs/claude/verify.md` 中和文章工作直接相關的規則。

### 2. 建立風格基準

- 閱讀至少三篇 Galen 近期、且形式或受眾接近的文章。優先從下列文章選擇：
  - `src/content/blog/2026-07-19-ai-coding-vs-shipping-code.md`
  - `src/content/blog/2026-07-19-kimi-k3-taiwan-stock-scapegoat.md`
  - `src/content/blog/2026-07-20-intuitive-gamer-fast-flat-reasoning.md`
  - `src/content/blog/2026-07-21-unity-cli-ai-agent-feedback-loop.md`
  - `src/content/blog/2026-07-24-ai-agent-confidence-is-not-evidence.md`
- 只提取可觀察特徵：開場方式、句長、技術詞密度、如何提出觀點、如何限制外推、如何收尾。
- 不要複製原句，也不要把共同結構變成每篇必用格式。
- 若風格仍有兩種合理方向且會大幅影響成品，再請使用者選擇；否則依最接近本題的文章前進。

### 3. 鎖定單一論點

先寫出下列四句工作筆記，不必放進成稿：

```text
核心問題：
本文主張：
讀者新增的判斷：
本文不處理：
```

確認以下條件後再研究：

- 標題提出的問題會在正文中被明確回答。
- 主張能由一篇文章講完，不需要借用無關題材增加份量。
- 「本文不處理」已排除至少一個容易擴張的旁支。
- 主張不是來源摘要，也不是任何 AI 文章都能使用的安全結論。

### 4. 建立主張—證據表

研究前先列出文章預計提出的主張，逐項填寫：

| 主張 | 類型 | 需要的證據 | 現有證據 | 限制 |
|---|---|---|---|---|
| 可驗證事實 | 事實 | 官方或第一手來源 | 來源連結 | 時效／範圍 |
| 因果或效果 | 研究結論 | 原始論文與方法 | 樣本、效果量 | 能否外推 |
| 實務建議 | 作者推論 | 事實＋推理鏈 | 推論依據 | 非官方標準 |

採用以下證據順序：

1. 官方文件、產品公告、原始資料。
2. 同行評審論文。
3. Working paper 或 preprint，明確標示尚未同行評審。
4. 可信媒體的一手採訪或資料整理。
5. 二手評論只用於補充觀點，不作為關鍵事實的唯一依據。

遇到會變動的產品、價格、政策、版本、研究或新聞，必須上網查核。技術主張優先引用官方文件；研究數字優先讀原始論文或正式摘要。

### 5. 進行證據邊界檢查

對每個來源問：

- 它直接測量了本文的對象，還是只提供相似情境的旁證？
- 樣本、任務、時間、模型、產品版本是否相同？
- 數字是百分比、百分點、相對變化還是絕對變化？
- 來源只證明「沒有公開資料」，還是真的證明「效果不存在」？
- 研究測量的是正確率、信任、接受率、信心歸因，還是其他變數？
- 作者建議是否超出來源實際涵蓋的功能範圍？

把限制寫在相關段落附近，不要只藏在文章最末的來源說明。

### 6. 撰寫初稿

依題目選擇最自然的結構，不強制套模板。通常包含：

- 一個具體情境、矛盾、數字或問題作為入口。
- 在前段清楚提出本文主張。
- 拆開容易混淆的概念。
- 用來源支持關鍵主張，並立即交代不能證明什麼。
- 提出作者自己的判讀、操作方法或決策框架。
- 用一個能回扣核心問題的句子收尾。

遵守以下寫法：

- 使用繁體中文；技術名詞保留英文，以讀者能理解為準。
- 用短段落與明確轉折，不連續堆砌研究摘要。
- 數字、日期、產品狀態與引述附上 inline link。
- 假設案例明寫「假設」或「示意」，避免看起來像真實數據。
- 用表格只在比較多個精確欄位時；不要為了完整感而加表格。
- 不必固定加入「帶走三句話」。只有確實能降低理解成本時才使用。
- 不把使用者會寫的所有題材硬混在一起；旁證只保留對核心論點必要的部分。

### 7. 做第一次對抗審查

把自己當成反對本文的 reviewer，逐項挑戰：

1. 標題是否比證據更強？
2. 本文最重要的觀點是否在前 20% 出現？
3. 刪掉來源摘要後，還剩下作者自己的什麼判讀？
4. 是否用間接研究暗示特定產品已被證明有問題？
5. 是否把 acceptance、engagement、人工批准或模型自評誤當 ground truth？
6. 建議是否從低風險情境突然擴張到 code、部署、權限或其他高風險範圍？
7. 是否存在只為容納某個題材而產生的支線？
8. 哪一段刪掉後，論證完全不受影響？
9. 反方最合理的說法是什麼？正文是否已公平處理？
10. 文章是否反覆說同一個結論，只是換用不同名詞？

只要任一問題成立，就先修稿，不要用來源數量替文章辯護。

### 8. 做客觀評分

每項以 10 分評估，低於 8 分就繼續修改：

| 面向 | 判準 |
|---|---|
| 事實正確性 | 日期、數字、功能範圍與來源一致 |
| 證據強度 | 核心主張有直接證據；旁證已標示限制 |
| 推論嚴謹度 | 事實、研究結論、作者推論沒有混寫 |
| 觀點辨識度 | 能指出一個不是通用口號的作者判讀 |
| 個人風格 | 符合既有語氣，但沒有機械複製文章模板 |
| 閱讀效率 | 每一節都推進核心問題，沒有可整段刪除的重複 |

不要因為文章是自己寫的而調高分數。評分後必須列出最強段落、最弱段落與仍無法由證據解決的限制。

### 9. 修稿

依下列順序修改：

1. 收窄過強的標題與核心句。
2. 把最有辨識度的觀點提前。
3. 補齊直接證據，或降低主張強度。
4. 刪除偏題研究、跨題材支線與泛化建議。
5. 合併重複結論，通常先嘗試縮短 10% 至 20%。
6. 重寫收尾，使它回到核心問題，而不是再摘要全文。

不要為達成縮字比例而刪除證據限制、安全界線或必要說明。

### 10. 驗證成品

純文章修改適用 TDD 豁免，但仍必須驗證：

```bash
git diff --check
npx vitest run
npm run build
```

另外執行：

- 抽出文章所有外部連結，確認可開啟；遇到反爬或需要登入時，改用瀏覽工具讀取並誠實記錄。
- 實際開啟文章 URL，確認 HTTP 200、標題、核心段落、Markdown 表格與 code block 正常呈現。
- 確認刪除的偏題內容未殘留在成品。
- `git status` 只包含本次文章工作；不要處理無關檔案。
- Push 後執行 `gh pr checks <PR>`，等 Vercel 完成。
- 在線上 preview 再確認一次最新 commit 的內容，不要只信本地 build。

文章 URL：

```text
http://localhost:4321/journal/{slug}/
```

### 11. 回報

先說明文章現在的核心觀點，再列出：

- 具體修改了哪些論證問題。
- 哪些來源是直接證據、哪些只是旁證。
- 仍存在但已明示的證據限制。
- 測試、build、連結與 preview 的實際結果。
- 最新文章 URL、PR 與 commit。

不要只回「已調整風格」或「已補資料」；必須指出改動如何讓文章更像 Galen，以及哪個觀點因此變得更清楚。
