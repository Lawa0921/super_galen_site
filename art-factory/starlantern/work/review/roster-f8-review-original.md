## 方法

1. 雜湊：19 件逐一重算 `work/repair/*` 的 sha256，與 `f8-assets.txt` 及 registry `repair.to_sha256` 比對；重算 `public/` runtime 檔，與 `repair.from_sha256` 比對；`repair.final` 路徑、`publish_with=f8`、`status=pending` 一併核對。19 件全部相符。
2. 像素差異：以 PIL 對 runtime 檔與修復檔做 RGBA 全圖比對。19 件的變更像素集合都剛好等於紀錄裡的 `pixels`（recolour）加 `cleared`（alpha 0）；recolour 像素的 alpha 不變、from/to 值與紀錄一致；cleared 像素的 alpha 為 0；`changed_pixels` 計數一致；修復檔沒有半透明像素。分類文件裡的 229 筆像素值與 registry 逐筆相符，而且與 repo 內的 `work/review/roster-f8-classification.md` 完全相同。
3. 偵測器重跑：以 repo 的 `sl_art.py` 對新舊檔重跑 `key_hue_pixels`、`outline_blend_pixels`、`lone_tint_pixels`、`pink_outliers`、外緣溢色、`roster_key_tint`、`bright_key`。另外自己掃一遍外緣上色相 268–335、飽和度 ≥ 0.6、亮度 ≥ 0.25 的像素，抓出偵測門檻剛好漏掉的殘留。
4. 目視：每件都看 12× 放大（bat 6×、局部 16–20×）的修復前後，分別放在 `#0f0e16` 與 `#ece8de` 上，另外看 3× 與 1×。每個變更像素與保留像素都核對 3×3 鄰域數值。lizard-scale 另外對照 R4 之前的原始 final（`work/sheet-icons-2/icon-lizard-scale.png`）。
5. FAIL 項的替代修法：把建議重分類的像素加進 key 集合，用 `sl_art._repair_median` 對 runtime 原圖試算。只做在 scratchpad，沒有寫進 repo。
