AI 漏跑測試，補一條。改到不該改的檔案，再補一條。都寫了還不聽？加上「必須」、「絕對禁止」，順便粗體。

這種心情我很能理解。把剛踩過的坑記起來，下次總可以省點事吧。

只是一路補下去，專案還沒做完，員工手冊先寫好了。工程師當一當，順便轉職 AI 人資。（技能樹又歪了。）

`CLAUDE.md`、`AGENTS.md` 這類檔案，就是留給 AI 開工前讀的專案交代：指令怎麼跑、哪裡容易壞、哪些事得先問人。至於實際讀到哪些檔案，要看工具和設定；檔名相似，不代表載入方式完全一樣。[Claude Code 說明](https://code.claude.com/docs/en/memory)、[Codex 說明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

我想問的是：補完這些規則，工作真的比較好做了嗎？

**我會優先留下能讓 AI 少猜一件事、少踩一個坑的規則。至於每條「必須」，也得想一下：它會替之後的每個任務，多加多少工作？**

## 有照做，然後呢？

來看[《Evaluating AGENTS.md》](https://arxiv.org/html/2602.11988v3)：這份 arXiv 預印本在 2026 年 2 月提出，本文讀的是 9 月 29 日更新的 v3。

與沒有規則檔相比，AI 自動產生的版本在 SWE-bench Lite、CTXbench 的平均推論費用分別增加 **20% 和 23%**，解題成功率沒有顯著改善。開發者版本的成功率改善也未達顯著。[研究結果](https://arxiv.org/html/2602.11988v3#S4.SS2)

Agent 確實更常照指示去測試、找檔案。移除專案原有文件後，自動產生規則檔的成績則較好；這組補充實驗未包含 Claude Code。[行為分析](https://arxiv.org/html/2602.11988v3#S4.SS3)、[附錄 B](https://arxiv.org/html/2602.11988v3#A2)

**研究沒有證明檔案越長就越差**：按長度分組，也看不出字數與成功率、單題成本有清楚關係。[長度分析](https://arxiv.org/html/2602.11988v3#A2)

範圍也要看：這是 Python 修題、Sonnet 4.5 和 GPT-5.2 等模型組合，主要看測試是否通過，沒有評量安全性。費用沒算人的收尾時間，也不能換算成訂閱額度。[方法與限制](https://arxiv.org/html/2602.11988v3#S5)

讀到這裡，我比較在意的反而是「有照做」這三個字。

假設請 AI 改一個按鈕上的錯字，規則卻要求每次開工都讀完整份架構、整理計畫、檢查所有模組。它真的照做了，最後字也改好了。

你說它有沒有聽話？有啊，還滿認真的。

但我只是想把那個錯字改掉。

這是假設情境，不是上面研究測到的個案。我從研究得到的提醒是：**除了檢查 AI 有沒有遵守規則，也該檢查我交代它做的事，對這個任務有沒有用。**

## 這個網站，就有值得寫下來的雷

拿自己的網站來看，比較有感。

這個專案的多語系文案有兩份：`src/i18n/translations/*.ts` 給伺服器端，`public/assets/i18n/*.json` 給客戶端。改到共用的 key，兩邊要一起更新。只改一份，可能看起來改好了，切個語言又看到舊字。

所以[專案的 CLAUDE.md](https://github.com/Lawa0921/super_galen_site/blob/2c352b967ef1694c79f55974b0da142c3759a2ad/CLAUDE.md)特別把它列出來。

這條我會留。因為它能回答一個很具體的問題：「我明明改了，為什麼畫面還是舊的？」也能告訴 AI 下一步去哪裡查。

另一個例子是測試指令。這裡的 `npm run test` 在本機互動終端會進入 Vitest 的 watch 模式；自動化驗證用 `npx vitest run`，就能明確指定跑完退出。從 [package.json](https://github.com/Lawa0921/super_galen_site/blob/2c352b967ef1694c79f55974b0da142c3759a2ad/package.json) 和 [Vitest 說明](https://vitest.dev/guide/cli.html)能查到這個差別，但既然它是常用入口，把差別直接寫清楚，我覺得值得。

所以「程式碼裡查得到」也不是一律不能寫。我的判斷會多一步：這件事是不是常用、容易猜錯，而且猜錯後會浪費時間？

相較之下，「請寫出高品質、易維護、符合最佳實踐的程式碼」，我就不知道能拿它來驗收什麼。

大家都想寫高品質程式碼。我也想，然後還是會生 bug。

換成「修改這個 key 時，要同步這兩個路徑」，至少知道少做哪件事會出問題。規則開始能幫忙，是從這種地方開始的。

## 「必須」前面，先補上「什麼時候」

我覺得規則最容易膨脹的地方，是某次有效的處理方式，被寫成以後每次都要做。

假設改到連線對戰，擔心兩邊協定沒一起更新，所以要求驗證雙方流程。這個要求很合理。但如果後來連改文章標點，也得開兩個玩家打完一場，那就有點忙了。

這同樣是示意，重點在適用範圍。

我會把規則寫到能回答三件事：**什麼改動會用到、要做什麼、怎樣知道做對了。**

下面用本站的雙檔文案來示範寫法，不是整份專案規範，也沒有取代既有的測試要求：

```markdown
## 修改多語系文案時

- 同一個 key 要同步更新：
  - src/i18n/translations/*.ts
  - public/assets/i18n/*.json
- 核對 en、ja、ko、zh-CN、zh-TW 五語的兩側 key 與文案。
- 開啟受影響頁面，切換語言，確認顯示的是新文案。
```

這幾行的用意很單純：讓 AI 知道這次有沒有踩進這個範圍，以及踩進去後怎麼出來。

涉及金流、部署、權限的底線，當然要保留。省幾個步驟，換來正式環境出事，這個帳怎麼算都不划算。適用範圍寫清楚，是讓該做的檢查真的做在對的地方。

而且有些底線要交給工具擋。Claude Code 官方也說明，`CLAUDE.md` 是提供給模型的上下文，不是強制執行的設定。[官方文件](https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)

不准動的資源，要在權限上限制；能自動檢查的錯誤，就考慮做成測試或檢查腳本。至於那句「絕對不准亂動」，我還是可以寫，但不能把整個身家押在它有讀到、也有照做上面。

## 拆成十個檔案，可能還是在讀同一本厚書

文件太長，直覺就是拆檔。我也喜歡把東西整理得看起來很有條理。（找不找得到是另一件事。）

但在 Claude Code 裡，用 `@路徑` 匯入的文件，會一起載入。只是把一大份內容拆開，再全部匯回來，上下文並沒有因此變少。官方另外提供依檔案路徑套用的規則，以及需要時才載入的 skills。[載入方式](https://code.claude.com/docs/en/memory#import-additional-files)

我會把這件事分開想：拆檔方便人維護；**讓 AI 這次只讀需要的內容，還得安排何時讀。**

像這個網站的規則入口，就有一張「何時讀哪份文件」的表。要查指令去看 commands，要查架構再看 architecture。這種寫法至少把用途講清楚了。

不過，光有路標還不夠。假設入口只寫「其他細節請見文件」，連什麼任務需要讀都沒交代，AI 可能漏掉；若寫成「開工前全部讀完」，又回到原點。

「改到登入流程時，先讀登入驗證規格」就具體很多。檔案裡還要有真的需要知道的東西；搬到別處的廢話，仍然是廢話。

這是我會採用的整理方向，不代表換成這種寫法，就已經實測能省多少 tokens。

## 刪一條之前，先知道它在救什麼

Claude Code 的官方建議裡，有個我滿認同的檢查方法：逐條想想，移除這行會不會讓 Claude 犯錯；也要觀察改完後，它的行為到底有沒有變。[官方實務建議](https://code.claude.com/docs/en/best-practices#write-an-effective-claude-md)

我會再補問一句：**當初讓我加上這條規則的那個錯，現在還會發生嗎？**

如果要動手整理，我會先挑一種常做的任務，留著舊版規則作比較。從相同的程式碼起點、相同模型與權限開始，分開跑舊版和新版；不要讓新版直接接收上一輪修好的成果。

看的東西也要對得上原本的目的：

- 為了避免雙檔漏改，就檢查兩側是否同步，還有切語言後的畫面。
- 為了避免指令跑不完，就看它實際用了什麼指令、有沒有正常退出。
- 為了省下收尾時間，就把自己提醒、檢查、補救的時間一起記下來。

再順手記錄耗時、用量和失敗次數。只挑一次剛好成功的結果，很難知道是規則改好了，還是那次運氣比較好。

這是我建議的試法，本文沒有做本站規則的前後對照實驗。不能看完研究、刪了幾行，就宣布生產力提升 30%。那個百分比會很漂亮，可惜是我編的。

有些規則防的是少見、但出一次就很痛的事，也不能因為試了幾輪沒碰到，就當它沒用。像正式部署的限制，就應該另外確認權限與阻擋是否有效，保留原本的保護。

## 規則也要有人收尾

我還是會寫 `CLAUDE.md`，也會繼續補專案裡那些不講很容易踩的坑。

只是每次要新增「以後一律……」之前，我想先停一下：這是在幫下一個任務省事，還是把上一次出包的整套處理流程，全部塞給它？

模型會換、專案會改，規則當然也得跟著整理。能指出真實地雷、說清楚何時適用，又有辦法檢查效果的，我會留下。失效的刪掉，重複的合併，只有特定工作需要的，就放到那份工作的說明裡。

**我想請 AI 幫忙把專案做完。員工手冊寫得再完整，也不會自己長出下一個功能。**
